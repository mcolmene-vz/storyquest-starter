## 2. Code-first rule (Decided)

Everything that can be built from code is built from code. The project has **one hand-authored scene** (`Boot`) containing a single `GameBootstrap` object. Every other object, scene content, Animator Controller, Timeline and Cinemachine camera is created at runtime from C# and data files, or generated by an editor script that lives in the repo.

Why: Claude Code works in files. A design that lives in editor clicks cannot be reviewed, diffed or rebuilt. The handful of unavoidable editor steps (importing a Synty package, setting a model's rig to Humanoid) are either automated with an `AssetPostprocessor` or written down step-by-step in `docs/EDITOR-STEPS.md`.

## 4. Runtime structure (Decided)

```
GameBootstrap (Boot scene, DontDestroyOnLoad)
  └── Services (plain C# singletons registered at boot)
        ProfileService   — profiles, active party
        SaveService      — JSON per profile + Ink state
        StoryService     — owns the Ink Story, binds external functions, raises tag events
        BattleService    — builds BattleState from data, runs BattleResolver, hands events to the presenter
        AudioService     — narration, music, sfx; respects narration toggle
        SettingsService  — difficulty, narration flag
  └── Flow (one state machine)
        Title → Profiles → Camp (story + shop + equip) → Battle → Camp … → Ending
```

Scenes beyond `Boot` are avoided in V1. Camp and Battle are **views** spawned and torn down by the flow state machine inside the single scene. This removes scene-loading bugs and keeps references in code.

## 5. Battle design (Decided)

- `BattleResolver` (Core) is a pure function: `Resolve(BattleState, Command) → (BattleState, IReadOnlyList<BattleEvent>)`. Events are small records: `TurnStarted`, `Attacked{attacker, target, damage, isWeakness, missed}`, `Healed`, `Defended`, `Defeated`, `Victory`, `PartyDefeated`.
- `BattlePresenter` (Runtime) consumes events sequentially and plays the **hit recipe**: cut to the attacker's Cinemachine camera → attacker animation → at the impact frame: `Time.timeScale = 0` for 60–100 ms (wait on unscaled time) → target plays `Hit` or `BigStagger` → knockback tween 0.3–0.5 m with ease-out → emission flash via `MaterialPropertyBlock` for 2 frames → particle burst at the hit point → Cinemachine impulse → damage number (world-space TMP, pops and fades).
- Animation events mark the impact frame on each attack clip; the presenter waits for the event, not a fixed delay.
- Determinism: the resolver takes a seeded random. The same seed and commands always produce the same events.
- Amended 2026-10-16 (M1 confirmation, details in §14.3): the event list is `BattleStarted`, `RoundStarted`, `TurnStarted`, `Attacked{attacker, target, damage, isWeakness, missed, skillId}`, `Healed`, `Revived`, `ItemUsed`, `Defended`, `Defeated`, `Victory{xp, coins}`, `PartyDefeated`. **No misses in V1**: `missed` is always false and stays in the record so the schema does not churn if accuracy is ever added. Defend halves every hit the defender takes until the defender's next `TurnStarted`. Enemy turns are also resolved in Core (`EnemyBrain` picks the command from a behaviour id and the seeded random). The hit recipe is a coroutine in `BattlePresenter` keyed off an `Impact` animation event; no Timeline asset in M1.

## 6. Characters and gear pipeline (Decided)

- Synty bodies imported as Humanoid. Mixamo clips downloaded "without skin" on the Mixamo Y-bot, imported as Humanoid, retargeted automatically.
- A hero prefab is generated by an editor script from `classes.json`: body (boy/girl) + class outfit parts + sockets `Socket_HandR`, `Socket_HandL`, `Socket_Back`, `Socket_Head`. Weapons are separate meshes parented to sockets at runtime. Armor swaps a Synty modular part.
- One Animator Controller for all heroes, generated by editor script, with states: Idle, Walk, Attack, Skill, Hit, BigStagger, Defend, Defeat, Victory. Class-specific attack clips are chosen through an `AnimatorOverrideController` per class.
- Enemies follow the same pattern with their own controller.
- Amended 2026-10-16 (M1): until Synty lands, the same pipeline runs on KayKit FBX imported as Generic (§11.4): one controller `Combatant` shared by heroes and enemies, an override controller per class and per enemy, prefabs generated into `Resources/Prefabs/Combatants/`. Sockets on the KayKit rig are the bones `handslot.r` / `handslot.l`; the Synty socket names above apply from M2 and the data field is `weaponSocket`, so the swap is a data change. Details in §14.1 and §14.4.
- Amended 2026-10-16 (M2 confirmation, details in §15.1–15.4). Synty bodies are extracted from the `.unitypackage` (never `-importPackage`) and imported as Humanoid. Mixamo clips are downloaded without skin on Y Bot and imported as Humanoid, with each take renamed to its file name. One prefab per hero variant, `{classId}_{body}` (eight), is built at generation time from `classes.json`: the variant's listed parts are kept and every other part is stripped. The sockets `Socket_HandR`, `Socket_HandL`, `Socket_Back` and `Socket_Head` are generator-made children of the avatar's hand, chest and head bones (`GetBoneTransform`), so no bone name reaches the data. **The generator pre-places weapons and armor** (the starter active, the class's shop item inactive), **and the runtime toggles them with `SetActive`**. This supersedes "parented to sockets at runtime" above: each class has exactly one upgrade per slot in V1, so a toggle is the whole runtime. The one `Combatant` controller still serves every combatant: hero overrides carry Humanoid clips, the troll's carries Generic KayKit clips. The troll stays the KayKit mannequin until the M4 enemy art.
- Amended 2026-10-16 (owner: no art spend in M2, details in §15.14). The "M2 confirmation" amendment above is suspended. Heroes stay KayKit on the Generic `Rig_Medium`, with KayKit clips and weapons under `handslot.r`. One prefab per class × look, `{classId}_{look}` (eight), with armor and both weapons pre-placed by the generator and toggled with `SetActive`. No Synty, no Mixamo, no Humanoid, no generated sockets.

## 7. Story integration (Decided)

- One Ink story per land (`land1/main.ink` includes `globals.ink` and `ch1.ink`…`ch5.ink`).
- The game reads **tags** on lines to drive presentation:
  - `# scene: village_day` — swap the camp backdrop
  - `# speaker: miller` — portrait and voice
  - `# audio: ch2_m_003` — narration clip id
  - `# battle: troll_grunt,troll_grunt` — start a battle; on return the game sets `battle_result` to `win` or `retreat`
  - `# reward: coins=20` / `# reward: item=potion`
  - `# shop` / `# camp` — open the shop or rest
  - `# memory: ask=millers_name` — memory callback marker
- External functions bound from C#: `heroClass(index)`, `partySize()`, `hasItem(id)`, `difficulty()`.
- Ink variables drive branching: `troll_weakness_known`, `lost_battle_ch3`, `remembered_millers_name`, and so on. The story bible lists them.

## 8. Saving (Decided)

- `SaveData { version, profiles[], settings }` serialized with Newtonsoft to `persistentDataPath/save.json`, written atomically (temp file + rename).
- Each profile stores hero, level, xp, coins, inventory, equipment. The land progress stores `story.state.ToJson()` plus chapter index.
- `version` field from day one; a migration hook that does nothing in V1.

## 9. Device layout (Decided)

- Landscape locked in Player Settings. iPhone and iPad both build from one target.
- Every UI root gets `SafeAreaFitter` (reads `Screen.safeArea`).
- Battle camera uses Cinemachine **Group Framing** on the party so 4:3 and 19.5:9 both frame all heroes; UI panels anchor to edges, never to absolute pixels.
- Minimum touch target 64 pt. No hover, no long-press.
- Amended 2026-10-16 (M2, §15.5): full-screen menus (from M2, the camp's Shop and Equip tabs) are laid out inside a **1600 × 900 reference-px box centred in the safe area**. At 1920×1080, match 0.5, the narrowest canvas is a true 4:3 iPad (iPad 9th generation: 1663 reference px wide), and the shortest safe area is a notched iPhone in landscape (about 925 px tall on the iPhone 11, 15 Pro and 17 Pro). The box fits both, and fits the 1.44:1 iPads (1728 × 1171) and the iPhones (about 1820–1890 px wide) with room to spare. Controls stay at least 170 reference px (64 pt, §14.5). The M2 review re-measures group framing with the Synty party against §14.4's checks. (2026-10-16, §15.14: the M2 party is KayKit; the checks are unchanged.)

## 12. Things we are deliberately not doing

Addressables, asset bundles, ECS/DOTS, scriptable render features beyond toon+outline, dependency-injection frameworks, reactive UI frameworks, multiple scenes, physics in combat, any network code.

## 13. Design notes (architect, 2026-10-15; M0 unless marked)

### 13.1 Creating the project

No Hub template and no `-createProject`: both add packages we would only delete (collab-proxy, visualscripting, multiplayer center, AI navigation, feature.development) and a hand-made SampleScene.

1. Commit by hand: `Packages/manifest.json` (§13.2); `ProjectSettings/ProjectVersion.txt` with `m_EditorVersion: 6000.3.26f1` and `m_EditorVersionWithRevision: 6000.3.26f1 (de8167e7440c)`; the `Assets/_Game` folders with the four asmdefs, their `csc.rsp` files, `link.xml`, and `Scripts/Editor/ProjectSetup.cs`.
2. `"$UNITY" -batchmode -projectPath . -quit` — the editor resolves packages, writes `Packages/packages-lock.json` and default `ProjectSettings/*.asset`, and rewrites core-package versions. Commit all of it with every `.meta`.
3. `"$UNITY" -batchmode -projectPath . -executeMethod Game.Editor.ProjectSetup.Run -quit` — idempotent, each step skips when its artifact exists: TMP essentials (amended 2026-10-16: `TMP_PackageResourceImporter.ImportResources` only queues an asynchronous `ImportPackage` that a `-quit` run never executes. Accepted: the step runs once and skips while that asset exists, so the reflection only matters if someone deletes the folder, and then the throw is the signal, not a silent fallback. The 37 files plus `TMP Settings.asset` are committed under `Assets/TextMesh Pro/`, where TMP looks for them, and are never moved), placeholder material, URP assets (§13.5), Boot scene (§13.4), `EditorBuildSettings.scenes = [Boot]`, Active Input Handling = Input System only (`activeInputHandler = 1` via a `SerializedObject` on `ProjectSettings/ProjectSettings.asset`; there is no public API), `BuildPipeline.ApplyPlayerSettings()` (§13.6), switch the active build target to iOS.

### 13.3 Assemblies, nullable, stripping

| asmdef (folder) | settings | references |
|---|---|---|
| `Game.Core` (`Scripts/Core`) | `noEngineReferences: true`, `autoReferenced: false`, `overrideReferences: true`, `precompiledReferences: ["Newtonsoft.Json.dll"]` | none |
| `Game.Runtime` (`Scripts/Runtime`) | `autoReferenced: false` | `Game.Core`, `Unity.InputSystem`, `Unity.TextMeshPro`, `Unity.RenderPipelines.Universal.Runtime`, `Unity.Cinemachine`, `Unity.Timeline`, the Ink runtime assembly |
| `Game.Editor` (`Scripts/Editor`) | `includePlatforms: ["Editor"]` | `Game.Core`, `Game.Runtime`, `Unity.RenderPipelines.Universal.Runtime`, `Unity.RenderPipelines.Universal.Editor`, `Unity.TextMeshPro.Editor`, `Unity.Timeline`, `Unity.Timeline.Editor`, `Unity.Cinemachine` |
| `Game.Tests` (`Tests/EditMode`) | `includePlatforms: ["Editor"]`, `overrideReferences: true`, `precompiledReferences: ["nunit.framework.dll"]`, `defineConstraints: ["UNITY_INCLUDE_TESTS"]` | `Game.Core`, `UnityEngine.TestRunner`, `UnityEditor.TestRunner` |

- References by assembly name, not GUID, so the files stay readable. Assembly names for TMP and Ink are as found under `Packages/` after import (expected `Unity.TextMeshPro` / `Unity.TextMeshPro.Editor`; Ink's as shipped). Unused references cost nothing; list the V1 set now so the asmdefs do not churn.
- Newtonsoft is referenced from Core only. The JSON surface (table loaders, `SaveData` serialization, the atomic write given a path string) lives in Core, which is what lets V1-SCOPE §13 test `SaveService` with a Core-only test assembly. Runtime hands Core text and paths; Core never sees Ink: the Ink state is stored as a `string`.
- If `UnityEditor.iOS.Xcode` does not resolve in `Game.Editor`, set `overrideReferences: true` and add `UnityEditor.iOS.Extensions.Xcode.dll` to its `precompiledReferences`; wrap the plist code in `#if UNITY_IOS`.
- Nullable: a `csc.rsp` next to each asmdef. Core: `-nullable:enable` and `-warnaserror:nullable` (pure C#, nullability is exact there). Runtime, Editor, Tests: `-nullable:enable` only, because `UnityEngine.Object` fake-null makes warnings-as-errors a fight not worth having. `com.unity.ide.visualstudio` propagates the rsp into the generated csproj, so VS Code agrees with the compiler.
- API level: `ApiCompatibilityLevel.NET_Standard` (Unity's name for .NET Standard 2.1) for `NamedBuildTarget.iOS` and `NamedBuildTarget.Standalone`, so tests and player compile against the same surface.
- Stripping: `ManagedStrippingLevel.Low` plus `Assets/_Game/link.xml` preserving `Game.Core` and `Newtonsoft.Json` (`preserve="all"`). Newtonsoft reaches constructors and setters by reflection; IL2CPP strips them and the bug appears only on device.
- `Game.Tests` exists in M0 with the asmdef and zero test files. ### 13.5 URP from code

`ProjectSetup.CreateRenderPipeline()`:

- `UniversalRenderPipelineAsset.Create()` → `Assets/_Game/Settings/URP/StoryQuest-URP.asset`, with its renderer saved next to it as `StoryQuest-Renderer.asset`. Use `Create()`; do not assemble a renderer from `CreateInstance` pieces (null default resources show up only on device).

- Asset values: render scale 1.0; MSAA 4x (near-free on Apple's tile-based GPUs and it is what makes low-poly edges and outlines clean); HDR off; main light per-pixel, shadows on, resolution 1024, distance 25 m, one cascade, soft shadows off; additional lights disabled; depth texture off; opaque texture off; SRP Batcher on; dynamic batching off; GPU Resident Drawer off (2026-10-16: set as `m_GPUResidentDrawerMode = 0` through a `SerializedObject` on the URP asset; the enum lives in `Unity.RenderPipelines.GPUDriven.Runtime`, which `Game.Editor` does not reference and will not for a value that is already the default); no post-processing and no renderer features (the hit flash is a material property, the shake is Cinemachine). Renderer: Forward (not Forward+), depth priming off, native render pass at its default.
- Quality levels (2026-10-16): `antiAliasing = 4` on every quality level, set in the same loop that assigns `QualitySettings.renderPipeline`; serialized as `m_QualitySettings[*].antiAliasing: 4` in `ProjectSettings/QualitySettings.asset` (verify: `grep -c "antiAliasing: 4"` equals the level count). Reason: on iOS the backbuffer is allocated at launch from the active quality level, before URP instantiates and copies its 4x into `QualitySettings`; a 0 there gives a 1-sample drawable for the first frame and the one-off pair "RenderPass: Attachment 0 was created with 1 samples but 4 samples were requested" / "EndRenderPass: Not inside a Renderpass" seen in the M0 simulator run. Not a lever: with Render Graph on, the renderer's `m_UseNativeRenderPass` applies only in Compatibility Mode, so it stays at its default; MSAA stays 4x (A12/A13 resolve it on-tile, and the message is about who created the drawable, not GPU capability). "Shadowmap RenderTexture requested without a depth buffer", seen once, is treated as simulator-only until a device log shows it: once at startup on device is harmless, per frame means the shadow atlas is re-allocating every frame and is a blocker that comes back to the architect with the Xcode console before any setting is changed.
- Colour space Linear (set in §13.6). The only knob allowed to change per device later is render scale, in M5, if iPad 8 misses 30 fps.

### 13.7 Toon shader (M1)

`Shader "StoryQuest/Toon"`, `Assets/_Game/Art/Shaders/Toon.shader`. All properties inside `CBUFFER_START(UnityPerMaterial)` so the SRP Batcher stays on: `_BaseMap`, `_BaseColor`, `_ShadeColor` (default 0.6 grey), `_RampThreshold` 0.5, `_RampSmooth` 0.05, `_OutlineColor` (near black), `_OutlineWidth` 0.015 (object-space metres), `_FlashColor` (white), `_FlashAmount` 0.

- Pass 1 `LightMode = UniversalForward`: main light only with its shadow attenuation; `band = smoothstep(t - s, t + s, NdotL * shadow)`; `col = albedo * lerp(_ShadeColor, 1, band) * light.color + albedo * SampleSH(normal)`; last line `col = lerp(col, _FlashColor.rgb, _FlashAmount)`. `multi_compile _MAIN_LIGHT_SHADOWS` only; no fog, no additional lights, no soft shadows.
- Pass 2 `LightMode = SRPDefaultUnlit`, `Cull Front`: vertex pushed along the object-space normal by `_OutlineWidth`, flat `_OutlineColor`.
- Passes 3 and 4: `ShadowCaster` and `DepthOnly`, URP's standard pass bodies copied in.
- Flash: `BattlePresenter` sets `_FlashAmount = 1` on every renderer of the target through a `MaterialPropertyBlock` for two frames, then back to 0. Never touch `renderer.material` (it instances the material and breaks batching). A lerp to white, not additive emission, because the scope asks for a white flash and it reads the same on dark and light albedo.
- Synty atlases and the KayKit texture both work as `_BaseMap`; the hero generator assigns this material.
- Amended 2026-10-16 (§15.14.3): `ToonForward` gains a palette-cell tint. Four `UnityPerMaterial` properties (`_CellA`, `_CellAMul`, `_CellB`, `_CellBMul`) and a `CellTint` helper multiply the albedo inside at most two cells of the texture's grid. No texture sample is added. It gives the KayKit heroes their skin tones and the Archer its gold bow.

### 14.3 `Game.Core` battle model

Folders: `Core/Data/` (models, `ITableSource`, `TableLoader`), `Core/Battle/`, `Core/Progression/`. Outline, not code:

```
enum Team { Hero, Enemy }          enum DamageType { Slash, Pierce, Magic, Blunt }
enum CommandKind { Attack, Skill, Item, Defend }     enum BattlePhase { Active, Won, Lost }
record Stats(int MaxHp, int Attack, int Defence, int Speed)
class Combatant { int Id; string Name; Team Team; string DefinitionId; int Slot; Stats Stats; int Hp;
                  DamageType AttackType; DamageType? Weakness; bool Defending; int SkillCooldown; string Behaviour; }
class BattleState { List<Combatant> Combatants; int Round; List<int> TurnQueue; int ActiveId; BattlePhase Phase;
                    Dictionary<string,int> Inventory; int XpEarned; int CoinsEarned; BattleState Clone(); }
record Command(CommandKind Kind, int ActorId, int TargetId, string? ItemId)
record BattleSetup(HeroSpec[] Heroes, string[] EnemyIds, Dictionary<string,int> Inventory, int Seed)
record HeroSpec(string ClassId, int Level, string Name)
interface IRandom { int Next(int maxExclusive); }     class SeededRandom : IRandom   // System.Random(seed); never UnityEngine.Random
record BattleStep(BattleState State, IReadOnlyList<BattleEvent> Events)
static class BattleFactory { BattleState Create(BattleSetup, GameTables); }
static class BattleResolver {
  BattleStep Start(BattleState, IRandom);              // BattleStarted, RoundStarted, TurnStarted
  BattleStep Resolve(BattleState, Command, IRandom);   // clones the input state first; the caller's state is never mutated
  Command EnemyCommand(BattleState, IRandom);          // behaviour id → command; called by BattleService when ActiveId is an enemy
}
```

- **Events** (one abstract record `BattleEvent`, sealed records below; ids are `Combatant.Id`): `BattleStarted`, `RoundStarted{round, int[] order}`, `TurnStarted{actor}`, `Attacked{attacker, target, damage, isWeakness, missed, string? skillId}`, `Healed{actor, target, amount, itemId}`, `Revived{actor, target, hp, itemId}`, `ItemUsed{actor, itemId, remaining}`, `Defended{actor}`, `Defeated{target}`, `Victory{xp, coins}`, `PartyDefeated`. `Attacked` with `skillId != null` is a skill; the presenter picks the clip and particle colour from it. Emission order for an attack: `Attacked` → `Defeated`? → `Victory`/`PartyDefeated`? → otherwise `TurnStarted` for the next actor (preceded by `RoundStarted` when the queue is empty).
- **Turn order.** Round-based. At `RoundStarted`, all living combatants are sorted by `Speed` descending; ties: heroes before enemies, then lower `Slot` first. The queue is fixed for the round; a combatant knocked down mid-round is skipped; a hero revived mid-round joins the next round. At a combatant's own `TurnStarted`: `Defending = false`, `SkillCooldown = max(0, SkillCooldown - 1)`.
- **Damage.** `base = max(1, floor(attacker.Attack × power) − target.Defence)`; `× 2` if `power`'s damage type equals `target.Weakness` (`isWeakness = true`, the presenter plays `BigStagger`); `× 0.5` (floor, min 1) if `target.Defending`. `power` is `attackPower` for Attack and `skill.power` for Skill. No variance, no critical hits, **no misses** (§5 amendment): with four stats and two multipliers the table is tunable in M4 and every number on screen is explainable; a 5-year-old reads a miss as a bug. The V1-SCOPE §7 miss SFX is left unwired; the lead tells the producer.
- **Defend.** Sets `Defending = true`; emits `Defended`. Halves every hit until the defender's next `TurnStarted`, not just the first, so a kid who defends against two trolls is not punished for it.
- **Skill.** Legal only when `SkillCooldown == 0`; on use `SkillCooldown = cooldownTurns`. Illegal commands (skill on cooldown, item count 0, dead or wrong-team target, actor not active) throw `ArgumentException`; the UI never offers them, so a throw is a bug, not a flow.
- **Item.** `potion` on a living hero: `Hp = min(MaxHp, Hp + amount)`, emits `ItemUsed` then `Healed`. `revive` on a knocked-down hero: `Hp = floor(MaxHp × amount)`, emits `ItemUsed` then `Revived`. Using an item is the hero's whole turn. Inventory counts are per party, not per hero.
- **Enemy behaviours** (`EnemyBrain`, Core): `attack_random_hero` = Attack a uniformly random living hero using `IRandom` (the grunt; this is what makes the determinism test meaningful). Reserved, not built in M1: `attack_lowest_hp_hero`, `heal_lowest_ally_or_attack`.
- **End of battle.** After any damage: all enemies at 0 → `Phase = Won`, `Victory{xp, coins}` with the sums of the enemies' `xp`/`coins`; all heroes at 0 → `Phase = Lost`, `PartyDefeated`. `Resolve` on a finished battle throws. Difficulty is **not** a Core concern: both outcomes are events, and `BattleService` applies the Always Win / Normal rule (§14.5).
- **Progression** (`Core/Progression/Progression.cs`, tests in M2): `LevelFor(totalXp, xpToReach)`, `StatsFor(classId, level, tables)`, `ApplyXp(totalXp, gained, xpToReach) → (newTotal, oldLevel, newLevel)`. M1's victory screen calls `ApplyXp` on each hero's in-memory XP and shows "Level up!" when the level changes; nothing persists until M3.

### 14.4 `Game.Runtime` battle presentation

**Flow.** `enum FlowState { Boot, Title, Profiles, Camp, Battle, Victory, Defeat, Ending }` laid out now; M1 drives `Boot → Battle → Victory | Defeat → Battle`. `FlowController` is a plain C# class owned by `GameBootstrap` (which runs its coroutines); it holds one active `IView { void Show(Transform uiRoot); void Hide(); }`; views build their objects in `Show` and destroy them in `Hide`, so nothing survives a state change by accident. `BattleView` and `ResultView` exist in M1; Title/Profiles/Camp are M2/M3 views on the same pattern. Services in M1: `BattleService`, `AudioService`, `DebugSettings` (stand-in for `SettingsService`, §14.5), `ResourcesTableSource`; `DebugParty` (`Runtime/Battle/`) builds the M1 `BattleSetup` (four heroes level 1 named by class, `troll_grunt`, `{potion: 2, revive: 1}`, seed from the clock) and is deleted in M3 when `StoryService` builds it from the `# battle:` tag, as `Spinner` is deleted now.

**`BattleService`.** `Start(BattleSetup)` → `BattleFactory.Create` + `BattleResolver.Start`; `Submit(Command)` resolves it, then while `ActiveId` is an enemy and `Phase == Active` calls `EnemyCommand` + `Resolve`, concatenating the events; the whole batch goes to `BattlePresenter.Play(events)` as one list. The presenter plays the list sequentially in a coroutine and, when it reaches a `TurnStarted` for a hero, enables the command panel and yields. Core's `BattleState` is never read by the presenter mid-playback; HUD values come from the events (and a snapshot of the state at the end of the batch), which is what keeps HP bars in step with the animation instead of jumping ahead.

**Folders.** `Runtime/Flow/` (`FlowController`, `FlowState`, `IView`), `Runtime/Services/`, `Runtime/Battle/` (`BattlePresenter`, `BattleStage`, `CombatantActor`, `AnimationEventRelay`, `BattleCameras`, `HitFx`, `DamageNumberPool`, `DebugParty`), `Runtime/UI/` (`SafeAreaFitter`, `UiFactory`, `BattleHud`, `CommandPanel`, `ResultView`, `DebugCorner`).

**Hit recipe (`BattlePresenter`, one coroutine per `Attacked`, in this order, numbers are the spec):**
1. `CM_Action` posed and raised to priority 20 (cut).
2. Attacker `CrossFade(Attack | Skill)`; `AudioService.Play(sfx)` for a skill at the same moment.
3. Wait for `AnimationEventRelay.Impact` (the `OnImpact` event the postprocessor put on the clip). Safety: if the clip ends without it, log an error naming the clip and proceed; never a fixed delay in the normal path.
4. Freeze: `Time.timeScale = 0` for **80 ms** (100 ms on a weakness hit) via `WaitForSecondsRealtime`, then `1`. The brain and impulse run on scaled time, so the whole frame holds.
5. Target `CrossFade(Hit | BigStagger)`, or `Defeat` if the event batch holds a `Defeated` for it; hit SFX.
6. Knockback: the target **root** transform (never a bone, no physics) slides along attacker→target by **0.35 m** (0.5 m weakness) with cubic ease-out over 0.25 s, then returns to its slot linearly over 0.35 s.
7. Flash: `_FlashAmount = 1` through one shared `MaterialPropertyBlock` on every renderer of the target for **2 frames**, then `SetPropertyBlock(null)` so batching resumes.
8. `HitFx.Burst(point, damageType)`: one `ParticleSystem` built from code (emit 12, sphere 0.2 m, speed 2–3, lifetime 0.3–0.4 s, size 0.08–0.15, gravity 0.5, billboard, `particle.mat`), colour per damage type (slash pale yellow, pierce light grey, magic violet, blunt orange, heal green); point = the target's `chest` bone.
9. `ImpulseSource.GenerateImpulseWithForce`.
10. `DamageNumberPool.Show(point, damage, isWeakness)`: 8 pre-built world-space `TextMeshPro` objects, billboarded to the camera each frame while active, scale pop 0 → 1.3 → 1 over 0.15 s, rise 0.6 m over 0.8 s, fade over the last 0.3 s; white, yellow and 1.4× for weakness, green with `+` for heals; `SetText("{0}", value)` so no string is allocated.
11. After the attacker's clip ends (or 0.7 s after impact, whichever is later) `CM_Action` priority 0, blend back to the group shot. Enemy turns get a 0.6 s beat after their `TurnStarted` so kids see whose turn it is.
`Healed`/`Revived`: actor plays `Skill`, target gets the green burst and number, no freeze, no knockback, no cut. `Defended`: `CrossFade(Defend)`, small white ring burst. `Victory`: all living heroes `Victory`, then `ResultView`. `PartyDefeated`: `ResultView` after the last `Defeat` clip.

### 14.5 Battle UI, difficulty, result screens

- **Sizing rule.** With the 1920×1080 reference and match 0.5, the canvas scale is `sqrt((w/1920)·(h/1080))`: 0.846 on an iPhone 11 (1792×828 @2x), 1.205 on an iPhone 15 Pro (2556×1179 @3x), 1.366 on the iPad 10 (2360×1640 @2x). 64 pt is therefore **≥ 170 reference px** in both dimensions on the worst case (iPhone 11: 170 × 0.846 / 2 = 72 pt; iPhone 15 Pro: 68 pt). Every tappable control in V1 is at least 170×170 reference px; `UiFactory` enforces it. All panels hang under the one `SafeArea` root from M0; nothing anchors to absolute pixels.
- **`UiFactory`** (`Runtime/UI/`): the only place that creates uGUI objects (`Panel`, `Button`, `Label`, `Bar`), TMP font from `Assets/TextMesh Pro/Resources` defaults, flat colours, no sprites in M1.
- **`CommandPanel`**, bottom-left: four buttons `Attack / Skill / Item / Defend`, 280×180 reference px each in a row, 24 px gaps. `Skill` shows "ready in n" and is non-interactable while on cooldown; `Item` opens a row of item buttons with counts (non-interactable at 0) and then a target step. Buttons respond on `onClick` only (no hover, no long press, §9).
- **Targeting.** Enemy targets: single enemy in M1, so Attack and Skill **auto-target** the only living enemy and fire on the first tap; the M4 multi-enemy picker (tap the enemy's HP label) is designed in M4, not stubbed now. Hero targets (potion, revive): tap one of the party HP cards; cards are 170 px tall for this reason. Revive lists only knocked-down heroes, potion only living ones.
- **`BattleHud`**: party cards bottom-right (class name, level, HP bar + `hp/max`, a small "DEF" tag while defending, "ready in n" under the skill), enemy card top-centre (name, HP bar), turn banner top-left reading "`{name}`'s turn" plus a flat yellow ring (a `Quad`, no collider) under the active combatant's feet. HP bars tween over 0.3 s when their event plays, never ahead of it.
- **Difficulty in M1.** `DebugSettings` (static, Runtime) holds `Difficulty { AlwaysWin, Normal }`, default **Always Win** (the youngest age band and "nothing is lost" is the safer default; the smoke list exercises both). ### 15.3 Eight hero variants

- **A variant is `(classId, body)`, body `"boy"` or `"girl"`; the prefab id is `{classId}_{body}`.** New `classes.json` fields per class (the M1 fields stay; `clips` holds the 15.2 names):
  ```json
  { "id": "swordsman", "…": "M1 fields",
    "model": "<modular FBX name, from the import task>", "weaponSocket": "Socket_HandR", "weaponMesh": "<starter SM_Wep_* name>",
    "variants": {
      "boy":  { "parts": [ "<part GameObject name>", "…" ], "colours": { "<key>": "#RRGGBB" } },
      "girl": { "parts": [ "…" ], "colours": { "…": "…" } } } }
  ```
  - **`parts`** is the complete list of modular parts shown for that variant: head, hair, eyebrows, torso, upper and lower arms, hands, hips, legs, attachments. It is explicit, with no inheritance between classes or bodies: what the file says is what is on screen.
  - **Rules for picking parts.** Faces stay visible: no closed helmets or masks, because a kid has to see their hero's face. Nothing scary: no skulls or demon pieces (STORY-BIBLE tone). Each class must read from behind, which is where the camera is (§14.4).
  - **`colours`** exists only in the bake branch below. Keys are the pack's character-shader colour property names without `_Color_`, in lower case, except skin, which comes from `tone` (below). Palettes may be copied from the preset materials in the scratch folder.
- **Sockets (the §6 names) come from the avatar, not from bone names.**
  - The generator adds `Socket_HandR`, `Socket_HandL`, `Socket_Back` and `Socket_Head` as empty children of `animator.GetBoneTransform(RightHand | LeftHand | UpperChest ?? Chest | Head)`.
  - Each socket's local pose comes from one of four constants in the generator. They are measured once so that a Synty weapon sits in the grip, and commented like KayKit's `GlobalScale`.
  - Each socket's local scale is `1 / bone.lossyScale`, so its world scale is 1 even on Synty's legacy 100× rig.
  - The Archer's `weaponSocket` is `Socket_HandL`, because Mixamo's bow clips hold the bow in the left hand. The other three classes use `Socket_HandR`.
- **Built at generation time.** `HeroGenerator` (new, in `Editor/`, called from `CombatantGenerator.Generate`, same determinism rules) writes the eight `Resources/Prefabs/Combatants/{classId}_{body}.prefab`. For each one it:
  - `Object.Instantiate`s the modular FBX, unlinked, as M1 does;
  - keeps the variant's `parts`, plus the class armor item's parts for that body (inactive);
  - destroys every other part;
  - adds the four sockets;
  - puts the starter weapon (active) and the class's shop weapon (inactive) under `weaponSocket`;
  - sets the toon material on every renderer, an Animator with the class override controller, and `AnimationEventRelay`; no collider, no rigidbody.

  The M1 hero prefabs (`swordsman`, `archer`, `mage`, `fighter`) are deleted. The generator fails, naming the problem, if a listed part or mesh is missing. Reason: eight prefabs of about 16–20 renderers each are reviewable and cost nothing at spawn. A runtime assembler would ship all 720 parts and repeat the work every battle.
- **Height check.** Every variant, with and without its armor, measured on body renderers only (weapons excluded), must stand 1.2–2.4 m; the generator logs it. A wrong file scale is fixed by `SyntyPostprocessor`'s constant, never by data (the §14.1 precedent).
- **Material: two branches, chosen by fact (b) from the import task.**
  - *Colour is in a texture:* one `Resources/Materials/Toon/synty_hero.mat` (`_BaseMap` = that texture) serves all eight variants, and there are no `colours`.
  - *Colour comes only through Synty's masks.* This is likely, since the store page sells "a custom shader to change colors". `HeroTextureBaker` (`Editor/`, called by `HeroGenerator`) composes one albedo per variant on the CPU from the base and mask textures.
    - Inputs: `SyntyPostprocessor` marks exactly those textures readable, uncompressed, no mips. No material references them, so they never reach the build.
    - The per-channel blend is copied from the pack's character shader and written as a table in the baker's header comment. Body-art, stubble and scar layers are left out.
    - Output: `Assets/_Game/Art/Textures/Heroes/{classId}_{body}.asset`, a `Texture2D` with mips, compressed to ASTC 6×6 by `EditorUtility.CompressTexture` and saved with `AssetDatabase.CreateAsset`, plus one `Resources/Materials/Toon/{classId}_{body}.mat` per variant.
    - Rejected: porting the masks into `Toon.shader`, which would cost three more texture samples and a dozen properties per fragment on an iPhone 11, for colours that never change at runtime; §13.7 stays as decided. Also rejected: PNG output, because `LoadImage` and `EncodeToPNG` live in `com.unity.modules.imageconversion`, which §13.2 dropped, and an editor-only step is not worth a module.
  - Weapons share `synty_weapons.mat` (the weapon atlas). Armor parts use their variant's material. Unchanged inputs give byte-identical outputs, checked like every other generated asset.
- **Skin tones (amended 2026-10-16, producer ruling 7).**
  - **Data.** Each variant carries `"tone": "light" | "medium" | "dark"`. `classes.json` gets one top-level `"skinTones": { "light": "#RRGGBB", "medium": "#RRGGBB", "dark": "#RRGGBB" }`, and skin colour comes only from there.
  - **`TableLoader` enforces the producer's rule:**
    - at least three distinct tones across the eight;
    - each tone on at least two variants;
    - the boy and girl of each class differ;
    - every tone appears in at least two classes.
  - **Starting assignment.** Swordsman boy light, girl dark; Archer boy medium, girl dark; Mage boy medium, girl light; Fighter boy dark, girl light. It is data: Martin may change it, and the loader keeps it inside the rule.
  - **Mask branch:** the baker's skin channel takes the tone colour.
  - **Texture branch, if it gives all eight the same skin.** The cheapest fix, in order:
    1. If the pack ships alternative atlases with other skin tones, each tone maps to one of them (data only).
    2. Otherwise `HeroTextureBaker` runs in recolour mode. It copies the atlas and replaces the skin swatch with the tone colour. The skin swatch is every texel within a small RGB distance of the atlas's skin colour, a constant measured once from the head part and commented like `GlobalScale`. This makes one texture and one material per tone used (three, not eight). It reuses the mask branch's code path: no shader change, no package.
- **Front captures for the tone check (producer ruling 7).** `Game.Editor.VariantCapture.Run` (`Editor/`) runs by `-executeMethod`, in batch mode **without** `-nographics` because it renders: `"$UNITY" -batchmode -projectPath . -executeMethod Game.Editor.VariantCapture.Run -logFile - -quit`.
  - **Scene.** In an unsaved empty scene, it instantiates each `{classId}_{body}` prefab at the origin, facing the camera, in its base outfit with its starter weapon. Lighting matches `BattleStage`: the M0 directional light and flat ambient.

  - Nothing is saved into `Assets/` and nothing ships. Battle shots do not count for this check: the battle camera sees the heroes' backs.

### 15.7 Performance and import settings

- **Expected group shot: about 80 SkinnedMeshRenderers, against §14.8's 45.**
  - Each of the four Synty heroes has about 15–19 skinned parts (12–13 body parts, hair, 1–4 attachments) plus a weapon; the troll has 6–9 parts.
  - Each renderer draws three passes: toon, outline and shadow caster. `DepthOnly` never runs, because the depth texture and depth priming are off (§13.5). That makes about 250 draw calls. SetPass does not grow (one shader, SRP Batcher).
  - Triangle counts come from the import task.
- **§14.8 budget amended for M2.** In the group shot (Frame Debugger, Game view at device resolution): at most 90 SkinnedMeshRenderers, 280 draw calls, 12 SetPass and 60k triangles. The iPad GPU reading (15.8, under 6 ms) decides whether that holds up. *Superseded 2026-10-16 by the counter budget in the next bullet: the Frame Debugger needs the editor GUI, and its SetPass figure was a modelling error.*
- **Budget in the probe's counters (amended 2026-10-16, ruling on M2-D3 finding 1).**
  - **What the counters count.** The `ProfilerRecorder` Render counters (`Draw Calls Count`, `SetPass Calls Count`, `Triangles Count`) count every draw the frame submits: toon, outline and shadow caster for each renderer (one shadow cascade, §13.5), plus the ground, the turn ring and the UI. `Triangles Count` counts triangles per draw, so each mesh counts about three times.
  - **Simulator numbers are device numbers.** These are CPU-side engine counts, so a simulator gives the same values as a device for the same content and resolution; only GPU timings differ. No device run is needed for them.
  - **They exist only in development players,** and every simulator build is one (next bullet).
  - **M1 reading on unchanged content** (iPhone 15 Pro simulator, group shot):
    - Draws 131 ≈ 42 renderers × 3 plus the UI. That is within §14.8's 160, which already included every pass.
    - Triangles 111k ≈ 37k unique mesh triangles × 3. That is within §14.8's 40k unique; §14.8's "2–4k per KayKit character" was low, the real figure is about 7k.
    - **SetPass 89 is real and was never within 12.** The outline is a second pass in the same shader. 89 ≈ 2 × 42 + UI is what happens when each object's forward and outline passes are drawn back to back, so the SRP Batcher cannot group across objects. §14.8's "≤ 12 SetPass" was the architect's modelling error, not something M1 broke, and M1's device soak held 60 fps with it.
  - **M2 budget, group shot,** read as the probe's `group draws / setpass / tris` (the maximum over a window) on a simulator development player:
    - draws ≤ 300 (about 3 × 90 renderers, plus ground, ring and UI);
    - SetPass ≤ 200 (about 2 × 90 + 20);
    - tris ≤ 180k (60k unique × 3);
    - at most 90 SkinnedMeshRenderers, summed from the generator's per-prefab renderer log for the four on-screen variants plus the troll.
  - **SetPass is a render-thread CPU cost**, so the iPad GPU reading does not judge it. The probe gains `rt` (15.8). Review rule: on the A16 iPad, `cpu` and `rt` each stay under 6 ms in the group shot (the same headroom argument as the GPU, §14.8).
  - **If `rt` misses, the first CPU lever** is to draw the outline in its own pass: URP's built-in `RenderObjects` feature, with the outline pass's `LightMode` changed to `Outline` and the feature added to the renderer by `ProjectSetup`. The SRP Batcher can then group every outline, and SetPass falls back to a handful. Taking it amends §11.3 ("no outline render feature"), and it is not taken before a device miss. Lever 2 below (mesh merge) cuts draws and SetPass together.
- **Every simulator build is a development player (amended 2026-10-16, M2-D3 finding 2).** Unity 6000.3 ships the iOS simulator player only as `Development_sim*`, so a simulator build logs Build type 'Development' whatever `SQ_DEV` and the Xcode configuration say.
  - Simulator runs are evidence for layout, framing and the render counters. They are never evidence for fps, `cpu`, `rt`, `gpu` or `mem`.
  - Device builds without `SQ_DEV` are release players; those numbers come from them (the D8 soak).
- **Levers, in this order, and only after a measurement misses** (the §14.8 rule):
  1. `shadowCastingMode = Off` on small parts (eyebrows, facial hair, hands): one generator rule.
  2. Merge each variant's parts into one SkinnedMeshRenderer per outfit state at generation time. That takes about 80 renderers down to about 10, and the armor swap becomes a mesh swap. Not built unless needed, because it adds sixteen generated meshes to git.
  3. Render scale, in M5 only (§13.5).
- **Memory:**
  - Hero albedos: at most 8 × 1024² ASTC 6×6 with mips, about 5 MB, of which four are on screen at once.
  - Weapon atlas and troll texture: under 2 MB. Clips: under 10 MB.
  - Only the parts the eight prefabs reference reach the build. The review reads the build log's asset report to confirm the modular FBX is not shipped whole.
  - Total app memory stays under 300 MB on the iPhone and flat over the soak (§14.8).
- **`SyntyPostprocessor`** (`Editor/Import/`), keyed on `Assets/ThirdParty/Synty/`, same shape as `KayKitPostprocessor`:
  - Character FBX: `animationType = Human`, `avatarSetup = CreateFromThisModel`, `importAnimation = false`.
  - Weapon FBX: `animationType = None`.
  - All models: `materialImportMode = None`, `isReadable = false`, `importBlendShapes = false`, `importCameras = importLights = false`, `useFileScale = true`, `globalScale = GlobalScale` (a constant the import task measures; expected 1), `meshCompression = Off`, and `optimizeGameObjects = false`, because the sockets are children of bones and the presenter reads chest and head transforms.
  - Humanoid mapping: if Unity's automatic mapping fails or maps a bone wrong (Synty's own mapping was in the `.meta` we do not copy), the fix is an explicit `humanDescription` bone map in this postprocessor, not a click.
  - Textures under `Synty/Textures/`: `sRGBTexture = true`, `maxTextureSize = 1024`, iOS ASTC 6×6, mipmaps on, bilinear, clamp, read/write off. Why 1024: Synty atlases are colour-swatch grids, and at 512 the first mip bleeds neighbouring swatches into each other. The exception is the baker's inputs: readable, uncompressed, no mips, full size, and editor-only.
  - `GetVersion()` is bumped with any rule change.
- `CombatantActor` finds the chest, head and right hand with `GetBoneTransform` when `animator.isHuman`, and by name otherwise (the troll).

#### 15.14.3 Looks and skin tones

- **A hero is class × look.** Each class has exactly two fixed looks that differ in skin tone, so eight looks replace the eight variants.
  - The prefab id is `{classId}_{look}`, and the look id is a tone id (`swordsman_light`, `swordsman_dark`).
  - Reason: no free pack we own has boy and girl bodies. Two looks per class keep eight choices, and they keep ruling 7's intent that no tone belongs to one class. Four fixed looks, one per class, could not meet that.
- **Mechanism: a palette-cell tint in `Toon.shader`.** It is the cheapest of the three options:
  - *Tint data* (`_BaseColor` per renderer) fails: the head mesh carries hair and eyes, the Barbarian's body carries skin and belt, and a multiply tints all of them.
  - *15.3's baker in recolour mode* works, but costs readable import rules for four textures, nine generated textures in git (eight looks plus the bow), and proof that `CompressTexture` output is deterministic.
  - *The cell tint* costs four material properties and one helper. It adds no texture sample and no texture asset, and stays SRP-Batcher-safe. 15.3 rejected porting Synty's mask shader because it cost three extra samples and a dozen properties per fragment; this costs neither.

  ```hlsl
  // Properties: _CellA ("Tint cell A (col, row, cols, rows)", Vector) = (0,0,0,0)
  //             _CellAMul ("Tint cell A multiplier, linear", Vector) = (1,1,1,1)      and the same pair for B.
  // UnityPerMaterial (the one block in HLSLINCLUDE): float4 _CellA; half4 _CellAMul; float4 _CellB; half4 _CellBMul;
  half3 CellTint(float2 uv, float4 cell, half4 mul)
  {
      float2 grid = max(cell.zw, 1);
      float2 c = min(floor(float2(uv.x, 1 - uv.y) * grid), grid - 1);   // row 0 is the image's top row
      return (cell.z > 0 && all(c == cell.xy)) ? mul.rgb : half3(1, 1, 1);
  }
  // ToonFragment, right after the albedo line (the textures clamp, so saturate makes the test match what is sampled):
  //   float2 uv = saturate(input.uv);
  //   albedo = saturate(albedo * CellTint(uv, _CellA, _CellAMul) * CellTint(uv, _CellB, _CellBMul));
  ```
  Only `ToonForward` changes. Materials that set neither cell (the troll, the ground) are unaffected, because `cell.z` is 0.
- **Data (`classes.json`).**
  - Top level: `"skinReference": "#F6C09C"`, the middle texel of KayKit's skin ramp (measured above).
  - Top level: `"skinTones": { "light": "#F6C09C", "medium": "#C68642", "dark": "#8D5524" }`. Each tone is what the ramp's middle texel becomes; `light` is KayKit's own skin, so its multiplier is 1.
  - Per class: `"looks"`, two tone ids, and `"skinCells"`: `["c0r0"]`, or `["c0r0", "c7r2"]` for the Mage. At most two, because the shader has two slots.
  - 15.3's `variants`, `parts`, `colours` and generated sockets are not used.
- **Generator.**
  - One material per class × look, `Resources/Materials/Toon/{classId}_{look}.mat`. `_BaseMap` is the class texture. `_CellA` is the first skin cell as `(col, row, 8, 4)`, and `_CellB` the second if there is one. The multiplier is `tone.linear / skinReference.linear` per channel, with `w = 1`, set with `SetVector`. Vector properties are not colour-converted, and the project is in linear colour space.
  - One `{itemId}.mat` per weapon with a `cellTint`, on the class texture, with `_CellA` set to that cell and the multiplier `to.linear / from.linear`.
  - The 8 × 4 grid is a generator constant, `KayKitPaletteGrid`, commented like `GlobalScale` with the date it was measured.
- **Starting assignment.** This is §15.3's, with the first look taking the old boy's tone and the second the old girl's:
  - Swordsman light and dark; Archer medium and dark; Mage medium and light; Fighter dark and light.
  - Light is on 3 looks, medium on 2, dark on 3, and every tone is in at least two classes.
  - `DebugParty`'s girl/boy/girl/boy seed becomes Swordsman dark, Archer medium, Mage light and Fighter dark, so the default party shows all three tones.
- **Ruling 7 in `TableLoader`** (restated in 15.14.8 q5):
  - each class has exactly two distinct looks, and each is a `skinTones` key;
  - at least three distinct tones across the eight looks;
  - each tone on at least two looks;
  - every tone used in at least two classes.
- **Hair** keeps each model's own colour (the Knight blond, the Mage black). Per-look hair would be a third cell slot on `c1r0`: data plus four shader lines. It is not in M2; ask the architect if Martin wants it.
- **Front captures.** `VariantCapture.Run` (15.3) stands. It writes eight `variant-{classId}_{look}.tga` in the starter outfit, plus `armor-swordsman.tga` (first look, helmet on) to confirm that the raised visor leaves the face visible (15.3's rule).

#### 15.18.1 Fingers

**Not acceptable as M2's end state.** The action shot shows the weapon hand close up, and a flat hand through a sword grip reads wrong. It is acceptable only while D6 lands the fix.

**Fix, code-first, no FBX edit: rename the duplicate finger bones during import, before the avatar is built.**
- `SyntyPostprocessor` gains `OnPostprocessMeshHierarchy(GameObject root)`. Unity calls it per root hierarchy before the avatar and clips are imported.
- For the hero FBX, it prefixes every transform under the left and right hand bones with `L_` or `R_` (for example `L_IndexFinger_01`), so finger names become unique.
- The explicit body map then adds the 30 finger bones (15 per hand).
- **Why this is safe:**
  - Skinning binds to transforms, not names.
  - Synty's clips already carry finger muscles: their avatars map 17–19 finger bones (fact g).
  - So the fingers animate: the sword grip curls, and the bow hand closes.
- **Verification:** the avatar is valid with 52 mapped bones, and a front capture of the Swordsman shows a closed grip.

**Fallback,** only if the hook cannot rename before the avatar step:
- The generator writes a static grip pose into each prefab: a curl constant per finger joint, measured once and commented like `GlobalScale`, applied to the transforms under each hand.
- Humanoid never writes unmapped bones, so the pose holds in every clip.
- Grip curl on the weapon hand, a lighter curl on the other.

A per-weapon `gripOffset` is still added only if a weapon visibly misaligns (§15.3).

#### 15.18.2 Skin tones

There is no regular grid in the atlas, so §15.15.2 branch 1 (cell tint) does not apply to heroes. A cell tint on a measured rectangle is rejected too: skin is not guaranteed to be one rectangle, and the pack's own masks are exact.

**Mechanism, in this order:**

1. **Alternative atlases as data, if they qualify.** D6's first step measures, in `SyntyImportCheck`, each of the 11 alternative hero atlases against `01_A`:
   - the mean colour inside the skin mask;
   - the mean absolute difference outside it.

   An atlas qualifies as a tone if it differs from `01_A` by at most 3/255 outside the mask (same clothes) and its skin is clearly lighter or darker. If light, medium and dark all qualify, each variant names its atlas in data (`"atlas"`). The chosen atlases are copied to `Textures/` (compressed, like `01_A`). No shader or baker work.
2. **Otherwise, a skin mask in `Toon.shader`.**
   - Under a local keyword, `_SKIN_TINT`, enabled on hero materials only: one extra texture sample (`_SkinMask`) and one colour (`_SkinTint`).
   - `albedo *= lerp(1, _SkinTint.rgb, mask)`, with `_SkinTint = tone.linear / skinReference.linear`, the same multiplier §15.14.3 used.
   - Every variant shares `01_A` and the mask; the tone is a material colour per variant, and the SRP Batcher stays on.
   - The mask is imported linear (sRGB off), single channel. Nothing else changes in §13.7.
   - Why not the 15.3 baker: it needs generated textures and proof that ASTC compression is byte-stable, to avoid one extra sample on four characters.
3. **The baker (§15.3) only if the masked tint shows visible seams on device.** Its readable inputs are separate editor-only copies (below), so the shipped `01_A` stays compressed and non-readable for the weapons.

**Which mask is skin.** Read from Synty's character Shader Graph (text) in the scratch folder: which channel of which `Mask_0n` is skin. Confirm it numerically: the mean `01_A` colour where that channel is above 0.5 must be skin-coloured. Use `Masks/Old/…_Mask_Skin_01` only if no current mask channel is skin.

**Readable copies, without touching the shipped atlas.**
- New `keep.txt` destination `EditorOnly/`: `SyntyPostprocessor` imports it readable, uncompressed RGBA32, no mips, full size.
- Nothing may reference it. The D8 audit checks that no material or `UiSkin` points into `EditorOnly/`, so it never reaches the build.
- The same package pathname may appear twice in `keep.txt` with different destinations (`01_A` in `Textures/` and in `EditorOnly/`). If `extract.sh` refuses that, D6 extends it.

**Ruling 7** is unchanged: `tone` per variant, `skinTones`, and the `TableLoader` checks (§15.15.2).
